Making it real · Blueprint

How we would build it, in the order that pays off soonest

Most of the parts exist as open source or cloud services. What Trellis adds is the typed graph spec, the pre-flight check, the gateways that enforce policy across frameworks, and the learning loop. So the plan is to adopt the plumbing, build the parts nobody else offers, and ship pre-flight first.

Roadmap

Five phases, each ending in something a team uses

Durations assume three to four engineers. Each phase has an exit test that real teams can verify, not a demo.

Pilots

Two pilot teams: one we know well, one that proves it is general

pilot 1 · customer zero

Production Reliability Copilot

It already has much of what Trellis assumes: an MCP server, OpenTelemetry traces, approval gates, read-only enforcement and 15+ agents, including a fan-out orchestrator and agent-to-agent delegation. Importing it is a strong first test of the spec. Expected first findings include loops bounded only by turn limits and missing eval sets: today only the primary query agent has an automated eval harness.

pilot 2 · proves generality

Support & Engineering Cross-Functional Teams

Something shaped like customer support triage or developer PR review, built in a different framework. If pre-flight finds real issues there too, the idea holds across teams. If it only works on one internal stack, we have built a single-app feature.

Risks

What could sink it, and what we would do about it

RiskLikelihoodMitigation
Scope creep. "A platform for everything" never ships.highPhase exits are real team outcomes. Pre-flight ships alone before any canvas work starts.
Cloud vendors converge. Foundry, Bedrock and Vertex add similar control planes.mediumStay neutral across clouds and frameworks. Lean on open protocols, so a vendor feature becomes another adapter.
Teams will not import. It feels like extra work for no gain.mediumThe importer does the work. The first value, pre-flight findings, arrives in minutes with no runtime change.
The platform becomes the crown jewels. Gateways sit in front of every credential.mediumManaged identities and short-lived tokens only. A separate blast radius per team. Gateways hold no long-lived secrets. Red-team it before phase 2 exits.
Forecasts are wrong and teams stop trusting them.low–mediumAlways show a band, never one number. Calibrate from traces. Publish forecast error per system.
Black-box harnesses limit pre-flight.certain, boundedBe explicit about glass, grey and black boxes. Enforce at the sandbox and gateway boundary.
The learning loop proposes bad changes.lowHeld-out sets, canaries, human approval, one-click rollback. Proposals are ranked by how often teams accept them.

How we would know it works

Measures for the first six months

Caught before production≥ 25

Pre-flight errors fixed before release across the two pilots.

Forecast error±25%

Calibrated monthly cost forecast against the actual bill, per system.

Spend under policy≥ 60%

Share of agent model spend that flows through Trellis gateways.

Time to first governed system< 1 day

From importing an existing agent to it running behind policy and traces.

Proposals accepted≥ 40%

Learning proposals that a team accepts after review. Lower means noise.

Skills reused≥ 3

Skills promoted from one system and used by another team's system.

Open questions

Decisions to make before phase 0

  • Sponsor and owner. Who funds a cross-team platform, and which group owns it after the pilots?
  • Second pilot team. Which independent engineering or support team has a live agent system and a reason to want pre-flight?
  • Runtime for native graphs. A general workflow engine (e.g. Temporal), or lightweight framework workflows?
  • Policy language. OPA/Rego, which platform teams often know, or Cedar, which is easier to read and analyse?
  • Build or join. Is there an internal platform team building part of this already, so Trellis becomes a layer on their work?
