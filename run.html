Runs that can wait, resume, replay and stop on purpose

A run is one instance of a graph with its own state. The runtime saves that state at every node boundary, so a run can wait hours for an approval, survive a crashed worker, be replayed for debugging or be forked to try a different model. Every step is a trace span tied to a canvas node.

Checkpoints

Resume, replay and fork are three uses of one checkpoint

A checkpoint holds the run's state, messages, pending calls and budget counters at a node boundary. Writes carry idempotency keys, so a resumed run never refunds twice.

Resume

After a crash, a deploy or an approval that took four hours. The run continues from the last checkpoint and repeats no paid step.

Replay

Rerun a past run with its recorded tool outputs to see why the model chose what it chose. Nothing touches real systems.

Fork

Branch from a checkpoint with one change: a model, a prompt, a tool. The Learn stage uses forks to compare variants on real cases.

Several goals at once

Goals share one budget, and the scheduler decides who waits

The PR review system pursues three goals in parallel branches. When the run budget is tight, the scheduler funds goals in priority order or in proportion, by team choice. Move the budget to see which goals finish.

Allocation

Dashed line = what the goal needs to finish. A goal that gets less stops at its budget close condition and reports what it found so far.

When goals conflict

An incident run may want to restore service (kill blocking session 87) and find the root cause (which needs session 87 alive to inspect). Policy decides the order instead of the model.

goals:
  - restore_service:  { priority: 1 }
  - find_root_cause:  { priority: 2 }
arbitration:
  - before: restore_service.any_write
    do: snapshot_evidence      # capture locks, plans, waits
  - restore_service.kill_session:
    tier: 3                    # still needs a DBA
